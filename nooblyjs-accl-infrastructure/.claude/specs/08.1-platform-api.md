# 8.1 Platform API and workloads

Needs: phase 6 (deploy from Git). Unlocks: every other phase 8 spec.

## Requirements

1. **R1** A launcher can create, change, deploy, scale, restart, suspend, resume and delete a workload **in process**,
   without HTTP, through `hosted.services.platform` (returned by `mount()`).
2. **R2** Every workload belongs to exactly one **tenant** (`tenantId`, an opaque string ≤ 64 chars from the
   launcher). Every call takes a tenant; a call can never read or change another tenant's workload. Asking for one
   that is not the tenant's answers `not_found`, never `forbidden`.
3. **R3** Workload kinds: `service` (public HTTP), `private` (HTTP reachable only inside the tenant), `worker` (no
   port), `job` (runs to completion, on demand or on a schedule the launcher keeps), `static` (8.8).
4. **R4** Every change that touches the cloud or a VM is an **operation** (architecture §7): the call returns
   `{ workload, operation }` at once; progress arrives as events.
5. **R5** Every event about a workload is emitted on `host.events` **and** on the launcher's `eventEmitter`
   (as `mount()` already does) with `tenantId`, `workload`, and, for deploys, `deployId`, `commit`, `status`.
6. **R6** Every cloud resource and container made for a workload carries the labels `noobly-tenant=<tenantId>` and
   `noobly-workload=<name>` in addition to the install labels (architecture §6.2).
7. **R7** The platform layer is **off unless asked for**: `mount(..., { platform: { enabled: true } })`. With it off,
   nothing in phases 0–7 changes.
8. **R8** Operators (`change-guardrails`) see every workload across tenants on a read-only **Platform** screen; tenants
   never see this accelerator's UI.
9. **R9** Works offline on the mock provider with the seed story extended by one tenant (`exclusivity-life`) and the
   NooblyJS Cloud services from its mock-ups.

## Design

### Records

`workloads/<tenant>/<name>.md` (name unique per tenant, `^[a-z]([-a-z0-9]{0,61}[a-z0-9])?$`):

```yaml
tenantId: exclusivity-life
name: api
kind: service                     # service | private | worker | job | static
region: af-south-1                # a catalogue region of a connected account
account: stevie-aws               # chosen by placement (8.2) unless pinned
source: { repo, branch, rootDir, gitConnection, image }      # image: a prebuilt image instead of a repo
build: { runtime: node22 | python312 | go123 | dockerfile, buildCommand, startCommand, dockerfile }
run: { port, command, env: [ { key, value } | { key, secretRef } | { key, link: { database | keyvalue | bucket } } ] }
plan: { cpu: 1, memoryMb: 2048 }  # reserved per instance; plan names belong to the launcher
instances: 2
healthCheck: { path: /health, timeoutS: 60 }
domains: [ api-exclusivity.nooblyjs.app ]
autoDeploy: { branch: main, webhookSecretRef }
status: live | deploying | failed | suspended | deleting
current: { deployId, commit, image }
createdAt, createdBy
```

`workloads/<tenant>/<name>/deploys/<id>.md`: `commit`, `message`, `trigger` (`push` / `manual` / `config`), `by`,
`operation`, `image`, `result`, `startedAt`, `endedAt`; body = build and rollout log.

### API (`services.platform`)

```js
const p = hosted.services.platform;
await p.workloads.create(tenantId, spec, { actor });        // → { workload, operation }  (create + first deploy)
await p.workloads.get(tenantId, name);
await p.workloads.list(tenantId, { kind, status });
await p.workloads.update(tenantId, name, changes, { actor });  // env/plan/instances/domains; redeploys only when needed
await p.workloads.deploy(tenantId, name, { commit, trigger, actor });
await p.workloads.scale(tenantId, name, { instances, plan }, { actor });   // plan change = rolling restart, no rebuild
await p.workloads.restart / suspend / resume / remove(tenantId, name, { actor });
await p.workloads.runJob(tenantId, name, { command, actor });  // kind: job
await p.deploys.list(tenantId, name, { limit, cursor });
await p.deploys.get(tenantId, name, deployId);
await p.usage(tenantId, { from, to });                       // reserved cpu·h, memory GB·h, bandwidth (8.5)
await p.capacity();                                           // per region: hosts, free cpu/memory (operator)
```

Errors are the accelerator's `ClientError` codes (`invalid` with `fields`, `not_found`, `conflict`, `quota`,
`unavailable`). `actor` is `{ id, name, kind }` for the audit trail; the launcher has already checked permission.

### Operations

`workload.create`, `workload.deploy`, `workload.scale`, `workload.restart`, `workload.suspend`, `workload.resume`,
`workload.delete`, `workload.job.run`. Their steps are defined in 8.2–8.4; 8.1 adds the types, the per-workload
lock (one operation at a time per workload) and the per-tenant concurrency cap (`INFRA_OPS_PER_TENANT`, default 2).

### Events

`infrastructure.workload.created|updated|deleted`, `infrastructure.workload.status` (`{ tenantId, workload, status }`),
`infrastructure.deploy.started|progress|succeeded|failed` (`{ tenantId, workload, deployId, commit, step, of }`),
`infrastructure.instance.started|stopped|crashed` (8.2). Worded for Activity like every other event; `quiet` for
progress.

### HTTP

`/api/v1/platform/*` mirrors the in-process API for operators only (`change-guardrails`), read-only in 8.1, so the
Platform screen and support tooling can see workloads. Tenants never call it.

### Mock

The mock runtime walks operations through their steps with `INFRA_MOCK_STEP_MS`, writes deploy logs, and supports
`failAt: 'workload.deploy.health'`.
