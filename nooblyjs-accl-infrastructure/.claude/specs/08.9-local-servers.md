# 8.9 Local servers

Needs: 8.1. Specs 8.2–8.5 run workloads on VMs this accelerator creates in a cloud and reaches over SSH. This spec runs
them on **servers you already own**: Ubuntu machines on your network that are enrolled, not created, and that run a
small agent which connects out to this accelerator. NooblyJS Cloud does not change: it calls the platform API (8.1), and
a workload whose region is a local site runs on that site's servers.

**Decided (2026-11-20).**

| | Decision |
| --- | --- |
| Control channel | An agent on each server connects **out** to the controller over a WebSocket (architecture O4; replaces roadmap 7.8). The controller never connects to a server. |
| Exposure | **LAN only** in v1. Decided again 2026-11-20: a launcher may serve a workload on its own URL by path (NooblyJS Cloud: `<base URL>/<workspace>/<service>/`, a reverse proxy to the endpoints below, as Render does on one URL). The endpoints themselves are `http://<bind address>:<port>`. No TLS of our own. |
| Seeing a workload | A **live log stream like Render's**: build and runtime logs, live tail, search, level filter, pause. No shell into containers in v1. |
| Agent | **Node 22**, no dependencies (Node's built-in WebSocket client), Docker Engine API over its Unix socket. The controller uses `ws` for the server side. |
| First server | **This Codespace**: Ubuntu 24.04, Docker 29 (cgroup v2), no systemd (PID 1 is `docker-init`), no user namespaces. |

## Words

A **site** is a group of local servers on one network, and is a platform region (`region: lan-dev`). A **server** is one
enrolled Ubuntu machine. The **agent** is the process on it. **Enrolment** turns a one-time token into a server's own
credential.

## Requirements

1. **R1 Sites.** Operators create a site: id (`^[a-z][a-z0-9-]{1,30}$`, e.g. `lan-dev`), name, `mode: lan`, system
   reserve per server (default 0.25 vCPU, 512 MB). A site appears as a region in `capacity()` and in the region list a
   launcher reads. A workload with `region: <site id>` places on that site's servers.
2. **R2 Enrolment.** *Add server* on a site makes a token (single use, valid 1 hour, stored hashed) and shows the
   install command. The install script (Ubuntu 22.04 or 24.04, run as root):
   - checks for Docker Engine; installs Docker's packages only with `--install-docker`, otherwise stops and says how;
   - creates the system user `noobly` in the `docker` group, installs the agent to `/opt/noobly-agent`;
   - writes `/etc/noobly-agent/agent.json` (controller URL, site, token), mode 0600, owned by `noobly`;
   - installs and starts a systemd unit when systemd is PID 1; otherwise (containers, Codespaces) prints the command
     that runs the agent in the foreground (`noobly-agent run`).
   On first connection the agent trades the token for a **server credential** (32 random bytes; the controller keeps
   only its hash; the agent keeps it 0600). The token cannot be used again.
3. **R3 Channel.** The agent dials `<controller>/infrastructure/agent/v1`. It sends `{ server, credential }` in its first
   frame, never in the URL. `wss://` always works. `ws://` is accepted only when the controller's host is `localhost`,
   a loopback address or a private (RFC 1918) address: the LAN mode. Heartbeat every 15 s. A server silent for 45 s is
   `offline`. The agent reconnects with backoff (1 s doubling to 30 s, with jitter).
4. **R4 Server facts.** On connecting and every 60 s: hostname, OS, kernel, CPUs, memory, free disk, Docker version,
   cgroup version, security options (user namespaces, rootless, AppArmor, seccomp), agent version, LAN addresses.
   `allocatable = total − reserve`. Missing hardening (e.g. no user namespaces) is a **warning** on the server, shown
   to operators, not a refusal.
5. **R5 A fixed command set.** The protocol has these commands and no others; each is checked against a schema on the
   agent as well as the controller: `network.ensure`, `image.build`, `container.run`, `container.stop`,
   `container.remove`, `container.list`, `health.check`, `job.run`, `logs.follow`, `logs.stop`, `stats.watch`,
   `facts.get`. **There is no command that runs an arbitrary shell command or `docker exec`.** The agent only touches
   images, containers and networks labelled with its install's id.
6. **R6 Containers.** 8.2 R2's limits and hardening (`--cpus`, `--memory` = `--memory-swap`, `--pids-limit 512`,
   `--cap-drop ALL`, `no-new-privileges`, read-only root where the runtime allows, never privileged or host network);
   user namespaces where the daemon has them. Labels `noobly-install`, `noobly-tenant`, `noobly-workload`,
   `noobly-instance`. `--restart on-failure:5`. A workload with a port gets a host port from 20000–29999, bound to the
   server's LAN address (to 127.0.0.1 when the site is a single development machine).
7. **R7 Placement.** 8.2's placement function over the site's **online** servers. Sites do not grow: when nothing has
   room the operation fails with `quota` and "Site <name> is full", which the launcher shows. Instances on a server
   that has been offline for 5 minutes are placed again elsewhere when there is room, and are `unknown` until then.
8. **R8 Builds.** The agent on the server chosen for an instance clones the repository and builds the image:
   - sources: `https://` Git URLs; `file://` paths only when the agent runs with `--dev` (tests and this Codespace);
   - a Git token arrives in the command frame and is used through a temporary 0600 credential helper that is deleted
     after the clone; it is never written to the repository or a log;
   - the image comes from the runtime template (Node 22, Python 3.12, Go 1.23; 8.3.1's pinned bases) or the repo's
     Dockerfile; it is tagged `noobly/<tenant-hash>/<workload>:<commit>`;
   - every build line streams into the deploy log as it happens, with secrets masked;
   - v1 has no registry: each server that runs an instance builds it (8.3's registry later).
9. **R9 Environment.** The launcher resolves its `secretRef`s when a deploy runs (a `resolveSecrets(tenantId, refs)`
   hook given to `mount()`; NooblyJS Cloud opens its sealed values). Values travel in the command frame, are written
   to `/var/lib/noobly-agent/env/<container>.env` (0600) for `--env-file`, deleted with the container, and never
   appear on a command line or in a log.
10. **R10 Exposure.** `services.platform.workloads.endpoints(tenant, name)` lists where the running instances answer
    (`http://<bind address>:<port>`; the site's bind address, 127.0.0.1 on one machine). The launcher routes to them:
    NooblyJS Cloud proxies `<base URL>/<workspace>/<service>/…` with the prefix taken off, passes none of its cookies,
    drops the app's Set-Cookie and sandboxes its pages (CSP `sandbox` without `allow-same-origin`), because the apps
    share its origin. Host-name routing, TLS and public exposure (a tunnel or 8.4 ingress) come later.
11. **R11 Logs and metrics.** The agent follows every labelled container's stdout and stderr with timestamps and
    streams `{ instance, at, stream, line }` with a cursor, meeting 8.5 R3–R5: in the launcher within 3 s, lines over
    16 KB cut and marked, resume from the cursor after a reconnect. Build output streams the same way. Docker stats
    every 10 s meet 8.5 R1. Both arrive through `services.platform.telemetry.subscribe()` and
    `infrastructure.telemetry.*` events, so NooblyJS Cloud's log viewer (its roadmap 4.3, 4.5) shows a live tail with
    search, level filter and pause.
12. **R12 Safety.** *Remove server* revokes the credential, closes the channel and refuses reconnection. Every command
    is recorded with the operation that caused it. Frames over 1 MB are refused. Enrolment and connections are rate
    limited per address. Another install's containers are never touched.
13. **R13 Agent version.** The controller states the agent version it expects; an older agent is flagged on the
    server row. v1 updates by running the install script again.
14. **R14 Egress firewall** (added 2026-11-23, from NooblyJS Cloud's security review). Tenant code (containers on
    tenant networks, builds' `RUN` steps on the default bridge) reaches the internet and DNS, but not the server itself
    or private, link-local (cloud metadata), shared, loopback or multicast addresses. The exceptions: replies on
    connections opened from outside (published ports), traffic to another Docker bridge (left to Docker's isolation),
    and the database relays, which listen on their own ports (15432–15452, never the database's) and are reachable only
    on the gateway of the network the packet came from. The rules match interfaces by pattern (`br-+`, `docker0`), so
    the agent, which is not root, never changes them: `noobly-agent firewall apply` (root) writes two chains
    (`NOOBLY-EGRESS` from `DOCKER-USER`, `NOOBLY-INPUT` from `INPUT`), replaced on every apply. `install.sh` applies it
    by default (`--no-firewall` to skip) and installs `noobly-firewall.service`, which applies it again at boot and when
    Docker restarts. The agent reports the last apply in its facts (`egressFirewall`); a server without it gets a
    warning. IPv4 only (the agent makes no IPv6 networks).

## Design

### Records (FsStore, under the accelerator's data folder)

- `sites/<id>.md`: `name`, `mode`, `reserve { cpu, memoryMb }`, `status`, `createdAt`, `createdBy`.
- `servers/<id>.md`: `site`, `hostname`, `facts`, `status` (`enrolling|online|offline|removed`), `credentialHash`,
  `allocatable`, `reserved`, `warnings[]`, `agentVersion`, `enrolledAt`, `lastSeenAt`.
- `enrolments/<token-hash>.md`: `site`, `expiresAt`, `usedAt`, `server`, `createdBy`.
- Instance records as 8.2's, with `server` in place of the host VM, plus `port` and `endpoint`.

### Provider: `local`

`src/providers/local/` implements the contract for a site: `account.verify` (at least one online server),
`account.regions` (the sites), `compute.list/get` (the servers), `compute.start/stop/restart` (refused: "Restart the
server yourself"), `compute.create/remove` (refused with `invalid`: "Local servers are enrolled, not created. Use Add
server."), `catalog.machineTypes` (none), `metrics.vm` (from the agent's stats).

### Runtime: `src/platform/runtime-local.js`

Implements the runtime interface the platform already calls (`build`, `rollout`, `health`, `run`, `remove`, `list`,
`images`, `setStatus`) by placing instances and sending agent commands. The platform picks the runtime by region: a
local site → `runtime-local`, otherwise the mock runtime (and later the cloud runtime of 8.2).

### Agent: `nooblyjs-accl-infrastructure/agent/`

Its own `package.json` (Node ≥ 22, no dependencies: Node's built-in WebSocket). Files: `protocol.js` (frame and command schemas, also imported by
the controller so both sides check the same rules), `docker.js` (the `docker` and `git` command-line tools through
`spawn()` with fixed argument lists, never a shell; built 2026-11-20 instead of the Engine API so builds need no tar
library), `commands.js`, `build.js`, `logs.js`, `bin/noobly-agent.js` (`run`, `enrol`, `status`),
`install.sh` (served by the controller at `/infrastructure/agent/install.sh`).

### Protocol (version 1)

JSON frames over one WebSocket: `{ v: 1, id, type, ... }`. Requests (`type: "command"`) get one `result` or `error`
frame with the same `id`. Streams (`log`, `build-log`, `stats`) carry `seq` and a cursor, and stop with `logs.stop` or
when the container is removed. The first frame is `hello` (`{ server, credential, agentVersion }`) or `enrol`
(`{ token, facts }`); nothing else is accepted before it.

### Controller: `src/services/agents.js`

Accepts agent connections on the launcher's HTTP server and keeps one session per server. The accelerator still never
listens on a port: **the host contract gains `host.onUpgrade(path, handler)`** (or `mount()` gets the `server`), and
each launcher (NooblyJS Cloud, `server.js`) passes its HTTP server's `upgrade` events through.

### Operator screens

The Platform page gains **Sites and servers**: create a site; *Add server* (the token and the command, copied with
one click, valid for an hour); servers with status, facts, warnings, reserved against allocatable, instances; *Remove
server*. Customers never see these screens.

### Mock and tests

An in-process **mock agent** speaks the same protocol over an in-memory pair of streams, with Docker faked in memory,
so enrolment → deploy → logs → offline → re-placement runs offline on Express 4 and 5. An opt-in test
(`INFRA_TEST_DOCKER=1`) runs the real agent against this machine's Docker with a `file://` sample app.

### NooblyJS Cloud (its roadmap phase 3)

Local sites join its region list (e.g. "Local network · lan-dev"). A service in a local site shows its LAN address,
and its logs come from telemetry. The create flow and the platform calls stay the same.

## Risks

- **The `docker` group is root on that server.** Anyone who takes over the agent controls the server. The agent has no
  shell command, runs as `noobly`, and only acts on schema-checked commands from an authenticated controller;
  rootless Docker comes later.
- **No registry:** a workload with instances on three servers builds three times. Acceptable for a LAN site of a few
  servers; 8.3's registry fixes it.
- **No TLS on the LAN:** traffic between users and workloads is plain HTTP inside your network. The agent channel is
  `wss://` except to a loopback or private controller address.

instance, at, stream, line }`, reach `services.platform.telemetry.subscribe({ onMetrics, onLogs })` and the
`infrastructure.telemetry.metrics|logs` events; `telemetry.metrics()` keeps 15 minutes per instance. A resumed log
stream asks Docker from the last timestamp delivered and drops the lines already sent, so none is lost or doubled.

restart refused in plain words, `metrics.vm` from the stats), registered with the provider registry for `local`
accounts. Rollouts announce the new endpoints (`infrastructure.workload.endpoints`, raw) as soon as they switch and
remove the old instances after a drain (`local.drainMs`, 2 s), so a launcher's proxy never sends a request to a removed
container. **All 8.9 tasks are done.** The exit check ran on this Codespace as NooblyJS Cloud's 3.0d (2026-11-20): two
instances under their limits, a rolling redeploy with every request answered, logs resumed after the agent was
stopped and started with nothing lost or doubled. *Remove server* refusing the next connection is covered by
`test/local-sites.test.js` rather than run against this Codespace, which would have to enrol again.

**Scale in place (2026-11-22).** A scale that changes only the count, at the same image and plan, adds or removes
instances on a local site (or a region without an ingress) as `rolling()` already did behind one: new instances
start, answer their health check and join the endpoints; extra ones (the newest on the busiest server) leave the
endpoints, drain for `drainMs`, then go. The others are never restarted. A new plan still replaces every instance. A
scale that fails removes only what it started, puts the workload's count and plan back and emits
`infrastructure.workload.scale_failed` (`{ tenantId, workload, reason, reverted, instances, plan }`).
`test/local-runtime.test.js`.

**Install ids (2026-11-22).** The seed wrote one fixed install id (`nc-seed01`) into every seeded `config.yaml`, so two
seeded installs on one Docker host each treated the other's containers as their own leftovers and removed them. Seeding
now picks a random `nc-<8 hex>` per data folder and a reset keeps it; a reset of a folder that still has `nc-seed01`
replaces it (`test/mount.test.js`). A folder seeded before this keeps `nc-seed01` until it is reset.

**Docker's error line (2026-11-22).** Docker 29's CLI follows a daemon error with "Run 'docker run --help' for more
information", and the agent kept only stderr's last line. A host port held outside our install (another install's
container, any other program) therefore failed the deploy with that line as its reason, and the retry on "port is
already allocated" never matched. The agent now reports the last line that is not usage text (`errorLine()`,
`test/agent-docker.test.js`). Found running two installs on one host: the second's instances now skip the first's
ports.

**Exit check:** this Codespace is enrolled as a server of site `lan-dev`. Through the platform API a Node sample app
builds on it, runs as two instances with limits that hold, and answers on its LAN addresses; its build and runtime log
lines reach `telemetry.subscribe()` within 3 seconds; stopping the agent marks the server offline and starting it again
resumes the logs without losing lines; removing the server refuses its next connection.
