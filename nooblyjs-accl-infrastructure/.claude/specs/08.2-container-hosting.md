# 8.2 Container hosting on shared VMs

Needs: 8.1. Today an app runs alone on a VM a person chose (architecture §9). A hosting platform needs many tenants'
containers per VM, limits that hold, and a scheduler that picks the VM.

## Requirements

1. **R1** Operators create a **host pool** per region (account, region, VM size, min/max hosts). The pool's VMs are
   ordinary VM records with `role: host` and `pool: <name>`, hidden from the VM list like database VMs.
2. **R2** Each instance runs as a container with `--cpus=<plan.cpu>` and `--memory=<plan.memoryMb>m`
   (`--memory-swap` equal, no swap), `--pids-limit 512`, a read-only root filesystem where the runtime allows, no
   privileged mode, no host networking, dropped capabilities, user namespaces on.
3. **R3** Placement reserves the plan's CPU and memory on a host; a host is never reserved beyond
   `allocatable = vm total − system reserve (0.25 vCPU, 512 MB)`. Instances of one workload go to different hosts when
   the pool has more than one.
4. **R4** When no host has room, placement grows the pool by one VM (up to `max`), or the operation fails with
   `quota` and the plain reason "Region af-south-1 is full", which the launcher shows.
5. **R5** Each tenant gets its own Docker network per host (`noobly-t-<hash>`); `private` workloads are reachable at
   `<name>.<tenant>.internal` from the tenant's other workloads and from nothing else. Cross-host traffic for
   private workloads goes over the cloud's private network to the host's private IP, filtered per tenant (8.4 ingress
   for public traffic).
6. **R6** `job` workloads run a one-off container that is removed when it exits; exit code, duration and peak memory
   are recorded; a job never runs twice at once.
   *Since 2026-11-22:* `runJob(tenantId, name, { command, actor, trigger })` (`trigger` is `manual` or `schedule`)
   refuses a second run while one is going (`conflict`, 409, "… is already running (since …)") rather than queueing it
   behind the first. A run emits `infrastructure.job.started`, then `.succeeded` or `.failed` (`{ tenantId, workload,
   runId, trigger, exitCode, durationMs, peakMemoryMb, reason }`); its output reaches `telemetry.subscribe()` like an
   instance's, tagged with the run's container. `services.platform.jobs.runs(tenantId, name, { limit })` lists runs
   newest first and `jobs.get(tenantId, name, runId)` returns one with its log; another tenant's job is `not_found`.
   The schedule stays the launcher's: the platform keeps `schedule` on the workload for its operators' screens only.
   `test/pools.test.js` (8.2.5), `test/local-runtime.test.js`.
   *Runs side by side (2026-11-22, for NooblyJS Cloud's Workflows):* a job's spec takes `concurrency` (1 to 20, default
   1; a record-only change). `runJob` refuses only when that many runs are going ("… is already running 3 of 3 runs at
   once"), takes `trigger: 'api'` as well, and `env: [{ key, value }]`: the run's own plain variables (up to 20, 64 KB in
   all), after the workload's so they win (a launcher's task name and input). Each run holds a **lane** of the
   operations engine (`run-1` … `run-n`): runs go side by side, a deploy, suspend or delete of the job neither waits for
   a run nor makes one wait (a run starts the image live when it starts), and runs do not count against the engine's
   per-tenant or per-account limits (they wait on a container; `concurrency` bounds them). On a local site or a host
   pool a run going reserves its plan for placement, so runs starting together find room one at a time; a run that
   finds none fails with the region's or site's "full" reason. `test/pools.test.js` (8.2 R6).
7. **R7** Container crashes are restarted by Docker (`--restart on-failure:5`); the crash, the exit code and the
   restart count are events (`infrastructure.instance.crashed`).
8. **R8** Suspend stops and removes a workload's containers and frees its reservations; resume places them again.
9. **R9** A drained host (operator action) takes no new instances and its instances are moved one by one with the
   rolling rules of 8.4 before it is deleted.

## Design

### Hosts run the agent (decision, 2026-11-20)

A pool's hosts are driven by the **noobly agent** of spec 8.9, not by SSH scripts: the host's first boot installs it
(`agent/install.sh`) with a one-time enrolment token (valid for an hour, used once, kept as a secret until the agent
enrols), and it connects out to the controller (`INFRA_PUBLIC_URL` + the mount path, `wss://` from a cloud). So cloud
hosts and local servers share one runtime (`src/platform/runtime-local.js`), one protocol and its checks (no shell, no
exec; every value Docker sees is validated in `agent/protocol.js`), and a host needs no inbound port for control. A
pool is a site of `mode: 'pool'` (`local/sites/pool-<name>.yaml`) whose servers are its hosts; `servers.place(region)`
turns a cloud region with host pools into the same kind of place as a LAN site. The scripts this spec first listed
(`container-run.sh` and the rest) are the agent's commands instead (`container.run`, `container.remove`,
`network.ensure`, `job.run`, `stats.watch`).

### Records

- `pools/<name>.yaml`: `purpose` (`host`, `builder` for 8.3, `ingress` for 8.4), `account`, `region`, `zone`,
  `machineType`, `diskGb`, `min`, `max`, `systemReserve`, `status`.
- VM records gain `role: host` (or `builder`, `ingress`) and `pool`; the agent's server record (`local/servers/`) names
  the VM (`vm`) and keeps `allocatable` `{ cpu, memoryMb }` (the machine less the system reserve) and `draining`.
- Instances: one list in `local/instances.yaml`, changed under one lock (the pool lock that placement reserves under),
  rather than a file per instance: `server`, `name`, `hostPort` (from 20000–29999), `image`, `status`
  (`starting|running|unknown|stopped|crashed`), `restarts`, `lastExitCode`, `aliases`, `startedAt`.

### Placement (`src/platform/placement.js`)

Pure function over records, so it is unit tested without a cloud: the online, not draining hosts of the region's host
pools → those where the plan fits (memory always; CPU fully on a pool, `cpuFloor: 1`; a quarter of it on a LAN site)
→ fewest instances of the same workload first (so instances land on different hosts), then least reserved after
placement (CPU share plus memory share: spread), then by name → reserved under the instances lock. Returns
`{ hosts }`, or `{ hosts, missing, grow: true }` / `{ hosts, missing, full: true }`. On `grow` the runtime asks the
pools service to add a host (`pool.grow`, up to `max`) and places again; past `max` the operation fails with `quota`
and "Region africa-south1 is full: there is no room for …".

### Steps

A deploy's rollout (8.1) places, makes sure the host has the image (built there from the recorded build until 8.3's
registry), creates the tenant network if absent (`network.ensure`), runs each instance (`container.run` with the
limits, the hardening flags, the labels `noobly-tenant`, `noobly-workload`, `noobly-instance`, and the private name
as a network alias), checks health, then switches and removes the old ones. `pool.grow`: name the host (`<pool>-<n>`)
and make its enrolment token → `vm.launch` (steps 1–2 with the host cloud-init: Docker with `userns-remap`, no Caddy
unless an ingress pool, the agent) → wait for its agent. `host.drain`: cordon (`draining`) → move each instance
(started and answering elsewhere before the old one is removed, growing the pool if it must) → delete the VM. Its
operation runs on `host:<vm>`, so the `vm.delete` it starts is not queued behind it.

### Mock

On the mock cloud no machine boots: `pool.grow` starts the in-process mock agent (`agent/mock.js`) with the token and
the facts of the VM's machine type. Its Docker (`agent/docker-mock.js`) keeps containers with their run arguments;
`crash(name, code)` follows Docker's restart policy, `resolve(from, name)` answers a private name as Docker's DNS
does, and `holdJobs()` keeps jobs running to show they never overlap. Mock hosts' agents are in memory: after a
restart of the controller they are offline (real hosts reconnect on their own).
