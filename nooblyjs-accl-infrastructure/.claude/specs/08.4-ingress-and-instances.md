# 8.4 Instances, ingress and rolling deploys

Needs: 8.2, 8.3, phase 3 (Caddy endpoints). Product v1 left "load balancers across several VMs" out of scope; phase 8
brings it in for platform workloads only.

## Requirements

1. **R1** Each region has an **ingress pool** (≥ 2 VMs in different zones for production) running Caddy, with a
   static IP each; the platform domain's DNS (`*.<platformDomain>`, e.g. `*.nooblyjs.app`) points at them.
2. **R2** Every `service` workload gets `<name>-<tenant-slug>.<platformDomain>` (the launcher may pass the exact
   host name) with a trusted certificate from the wildcard, and may add custom domains with their own certificates.
3. **R3** Ingress balances requests across the workload's healthy instances on any host (Caddy `reverse_proxy` with
   active health checks to the hosts' private IPs and instance ports); a dead instance leaves rotation within 10 s.
4. **R4** **Rolling deploy:** start new instances (one per old one, `maxSurge: 1`), wait until each passes its health
   check, add it to rotation, drain and stop one old instance (30 s drain), repeat. Zero failed requests with ≥ 2
   instances. A failed health check stops the rollout and keeps the old version.
5. **R5** A plan change (`scale` with a new plan) is a rolling restart with the same image; a count change adds or
   removes instances without touching the others.
6. **R6** Hosts accept instance ports only from the region's ingress VMs and from the same tenant's hosts (R5 of 8.2).
7. **R7** Requests and bytes out per workload are counted at ingress (for 8.5 and billing).

## Design

**Wildcard certificate:** Caddy with the DNS-01 challenge through the cloud's DNS (Cloud DNS / Route 53) for
`*.<platformDomain>`; the zone and its credentials are an operator setting (`INFRA_PLATFORM_DOMAIN`,
`INFRA_PLATFORM_DNS_ZONE`). Ingress VMs share certificates through Caddy's storage in the account's private bucket
(phase 4) so every ingress VM serves the same certificate.

**Custom domains:** Caddy **on-demand TLS** with an `ask` endpoint on this accelerator
(`GET /hooks/platform/tls-ask?domain=`, mounted before auth, answers 200 only for verified domains of a live
workload). DNS verification reuses the phase 3 DNS job (CNAME to the workload's platform host name).

**Config:** one generated Caddy site per workload in `/etc/caddy/platform/<tenant>/<workload>.caddy`, written and
reloaded on every ingress VM by the `ingress.sync` step (idempotent; writes only when the rendered file changed).
Upstreams come from instance records (`host private IP : port`).

**Records:** `ingress/<region>.md` (pool, VMs, static IPs, certificate status); workload `domains[]` gains
`{ host, kind: platform|custom, dns, cert }`.

**Steps** (`workload.deploy`, rollout part): 7 Place new instances · 8 Start and check each · 9 Add to ingress ·
10 Drain and stop old · 11 Record the deploy as current. `workload.scale` reuses 7–10.

**Mock:** a mock ingress keeps upstream tables in memory; a test "client" sends requests through it during a rollout
and counts failures.

## As built (2026-11-21)

- **Ingress pools** are host pools with `purpose: ingress` (pools.js): VMs with Caddy and the agent, each with the
  static public address every VM gets. Caddy runs with `--resume` (a systemd drop-in from the first boot) and the
  agent loads its whole config through Caddy's admin API on 127.0.0.1:2019 (`ingress.sync`), rather than writing a
  file per workload: the controller sends data (sites: host names, upstreams, health path, sleeping), protocol.js
  checks it (host names, upstreams only on the hosts' instance ports 20000–29999, no raw config), and
  `agent/ingress.js` renders Caddy's JSON. `src/platform/ingress.js` builds the sites from the workloads and the
  instance records, keeps one sync at a time per region, and records the last one (`ingress/<region>.yaml`).
- **Host names** (R2): a service's `domains` under `INFRA_PLATFORM_DOMAIN` (the launcher passes the exact name), else
  `<name>-<tenant>.<platformDomain>`. Other domains are custom. The wildcard's DNS-01 settings come from the region's
  cloud (`googleclouddns` with `INFRA_PLATFORM_DNS_ZONE` as the project, or `route53` with it as the hosted zone);
  Caddy must be built with that DNS module, and certificates are shared through Caddy's storage once phase 4's
  bucket exists (8.4.2 stays open until then).
- **Health and rotation** (R3): Caddy checks each upstream every 2 s and drops it after 2 failures; requests that
  meet a dead upstream are retried on another for up to 5 s. The runtime also syncs the ingress whenever an instance
  starts, stops, crashes for good or moves.
- **Rolling deploys** (R4, R5): in a region with an ingress pool the runtime starts one new instance, waits for its
  health check, syncs the ingress, then takes one old instance out (sync), waits `drainMs` (30 s unless the launcher
  says otherwise) and stops it. A failed health check removes the new ones and starts again any old ones already
  stopped, so the old version keeps serving. `workload.scale` with only a new count adds or removes instances and
  leaves the others alone; a new plan rolls them all.
- **Custom domains** (8.4.5): verified when the domain resolves (following CNAMEs) to one of the region's ingress
  addresses: the `ingress-domains` job, every minute. Only verified ones are served, and
  `GET /hooks/platform/tls-ask?domain=` (no sign-in) answers 200 only for them and for platform names.
- **Firewall** (R6): a host takes 20000–29999 only from the region's ingress VMs' private addresses; an ingress VM
  takes 80 and 443 from anywhere; set when a pool grows or loses a VM. Same-tenant traffic between hosts waits for
  8.2.8 (private names across hosts).
- **Counters** (R7): `ingress.counters` reads Caddy's per-host metrics; the `ingress-traffic` job turns each VM's
  totals into deltas (a restarted Caddy starts again from zero) and keeps hourly buckets per workload for 48 hours
  (`ingress/traffic.yaml`); `services.workloads.traffic(tenant, name, { hours })`.
- **Idle sleep** (8.4.8, added for the hosting product): a web service with `sleep: { afterMin }` (5–1440) and no
  request for that long goes to sleep (`workload.sleep`: its containers stop, its status is `sleeping`). Its site then
  answers 307 to `GET /hooks/platform/wake?host=&path=` on this controller (no sign-in), which wakes it
  (`workload.wake`), waits until it answers (up to a minute) and sends the visitor back. Private services and
  workers never sleep: nothing in front of them could hold a request.
- **Mock**: the mock agent's Docker keeps the last `ingress.sync` and answers `request(host, path)` as Caddy would,
  through a mock network of the pool VMs' private addresses, so tests send requests during a deploy and count failures.
