# 8.4 Instances, ingress and rolling deploys

Needs: 8.2, 8.3, phase 3 (Caddy endpoints). Product v1 left "load balancers across several VMs" out of scope; phase 8
brings it in for platform workloads only.

## Requirements

1. **R1** Each region has an **ingress pool** (≥ 2 VMs in different zones for production) running Caddy, with a
   static IP each; the platform domain's DNS (`*.<platformDomain>`, e.g. `*.nooblyjs.app`) points at them.
2. **R2** Every `service` workload gets `<name>-<tenant-slug>.<platformDomain>` (the launcher may pass the exact
   host name) with a trusted certificate from the wildcard, and may add custom domains with their own certificates.
3. **R3** Ingress balances requests across the workload's healthy instances on any host (Caddy `reverse_proxy` with
   active health checks to the hosts' private IPs and instance ports); a dead instance leaves rotation within 10 s.
4. **R4** **Rolling deploy:** start new instances (one per old one, `maxSurge: 1`), wait until each passes its health
   check, add it to rotation, drain and stop one old instance (30 s drain), repeat. Zero failed requests with ≥ 2
   instances. A failed health check stops the rollout and keeps the old version.
5. **R5** A plan change (`scale` with a new plan) is a rolling restart with the same image; a count change adds or
   removes instances without touching the others.
6. **R6** Hosts accept instance ports only from the region's ingress VMs and from the same tenant's hosts (R5 of 8.2).
7. **R7** Requests and bytes out per workload are counted at ingress (for 8.5 and billing).

## Design

**Wildcard certificate:** Caddy with the DNS-01 challenge through the cloud's DNS (Cloud DNS / Route 53) for
`*.<platformDomain>`; the zone and its credentials are an operator setting (`INFRA_PLATFORM_DOMAIN`,
`INFRA_PLATFORM_DNS_ZONE`). Ingress VMs share certificates through Caddy's storage in the account's private bucket
(phase 4) so every ingress VM serves the same certificate.

**Custom domains:** Caddy **on-demand TLS** with an `ask` endpoint on this accelerator
(`GET /hooks/platform/tls-ask?domain=`, mounted before auth, answers 200 only for verified domains of a live
workload). DNS verification reuses the phase 3 DNS job (CNAME to the workload's platform host name).

**Config:** one generated Caddy site per workload in `/etc/caddy/platform/<tenant>/<workload>.caddy`, written and
reloaded on every ingress VM by the `ingress.sync` step (idempotent; writes only when the rendered file changed).
Upstreams come from instance records (`host private IP : port`).

**Records:** `ingress/<region>.md` (pool, VMs, static IPs, certificate status); workload `domains[]` gains
`{ host, kind: platform|custom, dns, cert }`.

**Steps** (`workload.deploy`, rollout part): 7 Place new instances · 8 Start and check each · 9 Add to ingress ·
10 Drain and stop old · 11 Record the deploy as current. `workload.scale` reuses 7–10.

**Mock:** a mock ingress keeps upstream tables in memory; a test "client" sends requests through it during a rollout
and counts failures.
