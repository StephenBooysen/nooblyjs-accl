# 8.3 Builds and the image registry

Needs: 8.1, 8.2. Today `app.deploy` builds on the VM that runs the app (architecture §9). With several instances on
several hosts the image must be built once and pulled everywhere.

## Requirements

1. **R1** A workload builds from a repo's **Dockerfile** or from source with a **runtime**: `node22`, `python312`,
   `go123`, using the workload's root directory, build command and start command.
2. **R2** Builds run on **builder VMs** (a host pool with `purpose: build`), never on hosts that serve traffic, with a
   time limit (15 min default) and CPU/memory limits per build.
3. **R3** The built image is pushed to the account's **registry** (GCP Artifact Registry, AWS ECR; one repository per
   install, image `<tenant>/<workload>:<commit>`), and hosts pull it with read-only credentials.
4. **R4** The build log streams into the deploy record and as `infrastructure.deploy.progress` events, line by line,
   with secrets masked.
5. **R5** Build-time environment is limited to variables the tenant marks `build: true`; run-time secrets never enter
   an image layer.
6. **R6** Images older than the last 5 per workload are deleted from the registry; a failed build leaves the running
   version untouched.
7. **R7** A prebuilt image (`source.image`) skips the build; it is pulled from a public registry or copied into ours.

## Design

**Runtime templates** live in `src/build/runtimes/<runtime>.Dockerfile` (multi-stage, slim official base images
pinned by digest in `src/build/runtimes/bases.yaml`, refreshed by a script). The template takes `ROOT_DIR`,
`BUILD_COMMAND`, `START_COMMAND` as build arguments; defaults per runtime (`npm ci && npm run build --if-present` /
`npm start`; `pip install -r requirements.txt` / `gunicorn` if present else the start command; `go build -o app ./...`
/ `./app`). The template is written into the build context; a repo Dockerfile wins when `runtime: dockerfile`.

**Provider contract** gains `registry: { ensure(region), pushCredentials(), pullCredentials(), list(image), remove(image) }`.
Mock: an in-memory registry. GCP: Artifact Registry Docker repository `noobly-<install>`; hosts use the VM's service
account with `artifactregistry.reader`. AWS: one ECR repository per tenant/workload under prefix `noobly-<install>/`;
hosts use an instance profile with pull rights.

*As built (2026-11-21):* hosts pull with short-lived credentials from `pullCredentials(region)`, not with the VM's own
identity. GCP mints a token for the reader service account `noobly-pull`; AWS assumes the reader role `noobly-pull`.
That needs no service account or instance profile on each VM. ECR's repository per image is made by the optional
`registry.prepare(ref)` just before the push. The access is in `docs/least-privilege.md`.

**Steps** (`workload.deploy`, build part): 1 Pick a builder · 2 Clone (the Git connection's token through
`GIT_ASKPASS`, as today) · 3 Prepare the build (template or Dockerfile) · 4 Build (`docker buildx build`, BuildKit
cache in the builder's local cache per workload) · 5 Push · 6 Clean up the build directory. Rollout follows in 8.4.

**Mock:** builds succeed after N steps with a canned log; `failAt: 'build'` gives a failing log.

## As built (2026-11-21)

Builds run on the noobly agent (spec 8.2's decision), so the build commands are agent commands and every value is
checked in `agent/protocol.js`:

- **Templates** live with the agent, which does the building and is shipped to servers on its own:
  `agent/runtimes/<runtime>.Dockerfile` and `agent/runtimes/bases.json` (JSON, not YAML: the agent has no
  dependencies). `scripts/refresh-bases.js` (`npm run refresh-bases`) pins each base to Docker Hub's current digest.
  The agent fills the template's `{{slots}}` with JSON strings, so a build or start command is always one argument of
  an exec-form `RUN` or `CMD`, whatever it contains. Go builds in the toolchain image and runs on slim Debian.
- **Build-time variables** (R5): a variable is given to the build when the service marks it `build: true` (it stays a
  run-time variable too). They reach the build as a BuildKit secret (`--secret id=build-env`, a 0600 file deleted
  with the build folder) that the template sources for the build command only, so no value is in a layer or the
  image history; a repository's own Dockerfile can mount the same secret. Their values (and the registry passwords)
  are masked in the streamed log. Secrets are opened for the build only when marked.
- **Builder pools** are host pools with `purpose: builder` (the spec's `build`), created on the Platform screen. A
  build takes one slot of a builder: a host runs as many builds at once as its allocatable holds of the pool's build
  limits (default 1 vCPU and 2 GB; at least one), because BuildKit has no per-build CPU or memory limit; the time
  limit (default 15 minutes) stops the build. All slots busy: the builder pool grows (up to its max), else the build
  waits for a slot. A region without a builder pool, or whose account has no registry, builds on its hosts and says
  so in the log; a LAN site always does (8.9 R8).
- **Registry** (`registry` in the provider contract, an optional area: `src/providers/contract.js`): the mock keeps
  images in the mock cloud with Artifact Registry's or ECR's host and path. A build is pushed as
  `<registry path>/<tenant hash>/<workload>:<commit or deploy hash>` with short-lived push credentials (`image.push`,
  logged in through a temporary Docker config that is deleted after); hosts pull with read-only credentials
  (`image.pull`) and tag the image into the install's own namespace, the only images `container.run` accepts. The
  builder removes its copy after the push and keeps its build cache.
- **Retention** (R6): image records keep each workload's last five and any an instance still runs; the ones dropped
  go from the registry and from the servers (`image.remove`). The daily `image-retention` job prunes what the
  registry holds beyond that. A failed build fails the deploy before the rollout, so the running version stays.
- **Prebuilt image** (R7): `source.image` is pulled by each host (no copy into our registry), under our own tag.

Steps in the deploy log: picking a builder (and growing or waiting), cloning, the template, the build, pushing; then
each host's pull as the rollout places instances.
